Character Map & Foundation

Fondasi
Person
Peta lima character dan adaptasi bahasa, dilengkapi transkrip percakapan teknis dua giliran adaptasi (two-turn adaptation repair), perbandingan skema basis data sebelum–sesudah commit, serta jadwal pengelolaan beban kerja.
CatatanIdentitas dan Status Evidence

Mahasiswa: Muhammad Nabil Aizar Ramadhan
Dokumen ini disusun untuk memenuhi lembar kerja refleksi dan pemetaan peran komunikasi pada Minggu 1. Seluruh lampiran artefak dicantumkan secara lengkap, valid, dan dapat diverifikasi langsung (inline plain-text) tanpa mengandalkan tautan eksternal.

Kompetensi Target

Membedakan person, personality, dan character serta memilih objective, repertoire, dan language yang sesuai dengan konteks komunikasi interpersonal dan akademik melalui observasi adaptasi respons langsung.

1. Pemetaan 5 Character Komunikasi

Berikut adalah pemetaan lima character yang saya bawakan di lintas domain kehidupan:

Domain Kehidupan Person & Relationship Peran & Character Objective & Responsibility Repertoire & Language Register Risiko & Tindakan Pencegahan
1. Intra-Self (Diri Sendiri) Diri sendiri setelah evaluasi draf tugas Reflective Learner Memisahkan kesalahan teknis dari identitas diri; mengevaluasi fakta secara objektif. Jurnal evaluasi berbasis fact vs story; register bahasa introspektif dan netral. Terjebak self-blame; mewajibkan pencatatan 3 data fakta sebelum mengambil kesimpulan.
2. Keluarga / Sahabat Adik kandung yang memilih fokus studi Supportive Mentor Mendampingi pemetaan opsi tanpa memaksakan kehendak atau menggurui. Pertanyaan terbuka, paraphrasing, register bahasa kasual-ramah dan empati. Terdengar menggurui (paternalistic); meminta izin sebelum memberikan pandangan.
3. Profesional / Akademik Rekan pengembang modul basis data Technical Coordinator Memastikan batas waktu commit dan skema API disepakati secara eksplisit. Check-in singkat, pembuatan opsi terstruktur, register teknis presisi (plain text). Penggunaan asumsi sepihak; mengonfirmasi ulang setiap kesepakatan secara tertulis.
4. Kelompok / Komunitas Anggota tim proyek tugas besar Facilitative Collaborator Membuka ruang partisipasi setara dan memfasilitasi pembagian beban kerja. Round-robin summary, klarifikasi ekspektasi, register dialogis dan rasional. Suara dominan menguasai diskusi; memberikan giliran bicara kepada anggota yang pasif.
5. Dunia / Publik Pembaca umum / Pengguna sistem Clear Knowledge Translator Menyampaikan gagasan teknis menjadi langkah practical yang relevan dan mudah dipahami. Analog grafis, penyederhanaan jargon, register bahasa umum yang ramah dan lugas. Terjebak jargon dumping; menguji draf bacaan pada audiens awam sebelum dipublikasikan.

2. Pembedaan Konseptual & Perubahan Register Bahasa

Membedakan Person, Personality, dan Character

  • Person: Individu nyata utuh dengan segala kompleksitas dan latar belakangnya (misalnya: Rekan Fakhri sebagai anggota tim proyek pengembang perangkat lunak).
  • Personality: Kecenderungan sifat atau temperamen bawaan individu yang relatif stabil (misalnya: Fakhri cenderung introvert, analitis, dan berhati-hati dalam menyampaikan pendapat).
  • Character: Peran komunikasi deliberatif yang diambil oleh person pada konteks dan sasaran tertentu untuk mencapai objective spesifik (misalnya: Fakhri mengambil peran Backend Specialist saat berdiskusi teknis, sementara saya mengambil peran Technical Coordinator).

Demonstrasi Perubahan Register Bahasa

Ketika mengomunikasikan masalah penundaan commit basis data: * Ke Character Teman (Informal/Kasual):
> “Ri, aman kan? Santai aja, kalau ada kendala koneksi atau lokal, kabarin gue ya biar bisa dibantu.” * Ke Character Technical Coordinator (Profesional/Eksplisit):
> “Fakhri, berdasarkan catatan jadwal jam 13.00 WIB draf skema basis data belum terunggah di repositori main. Apakah ada kendala pada virtual environment lokal, atau kita perlu sinkronisasi rute API sekarang?”

A. Transkrip Percakapan Teknis Verbatim (Dua Giliran Adaptasi / Two-Turn Repair Protocol)

================================================================================
TRANSKRIP PERCAKAPAN INTERAKSIONAL (LOG DUAL-TURN ADAPTATION)
================================================================================
[14.05 WIB] Nabil  : "Fakhri, saya periksa branch main belum ada commit baru untuk skema user entity. Apakah ada kendala di lingkungan lokal?"

[14.08 WIB] Fakhri : [Target ragu-ragu, jeda ketik 2 menit] "Iya Bil... maaf banget. Saya ketahan di penyusunan relasi foreign key antara modul user dan authentication entity. Takut bentrok sama skema kamu, jadi ragu mau push." 
                     --> [SIGNAL LEMAH DETECTED: Keraguan akibat ketakutan konflik kode / breaking change]

[14.10 WIB] Nabil  : [ADAPTASI GILIRAN 1 - REPAIR 1: Mengubah pendekatan dari menagih deadline menjadi isolasi modul]
                     "Terima kasih infonya, Fakhri. Memang riskan kalau disatukan sekarang. Bagaimana kalau kita pisahkan skema auth ke tabel terisolasi dulu saja supaya kamu tidak merasa terbebankan konflik skema saya?"

[14.12 WIB] Fakhri : "Hmm, kalau dipisah tabelnya sih lebih aman... tapi saya masih belum yakin apa drafnya layak di-push sekarang."
                     --> [SIGNAL LEMAH DETECTED: Kebingungan standar kelayakan draf mentah]

[14.13 WIB] Nabil  : [ADAPTASI GILIRAN 2 - REPAIR 2: Memangkas standar kelayakan & menetapkan target waktu mikro]
                     "Tidak perlu rapi dulu, draf mentah lokal pun tidak masalah. Kalau kamu push draf terisolasinya dalam 10 menit ini, saya yang akan sesuaikan rute API-nya dari sisi saya. Gimana?"

[14.14 WIB] Fakhri : [STATE CHANGE: Yakin & Sepakat] "Nah, kalau gitu jelas! Setuju Bil. Saya isolasi tabel auth-nya lalu push draf mentahnya sekarang."
================================================================================

B. Tabel Observasi Signal Lemah & Perubahan Strategi Komunikasi

Giliran (Turn) Signal Lemah Target Terdeteksi Strategi Awal (Sebelum Adaptasi) Penyesuaian Strategi Komunikasi (Repair / Sesudah Adaptasi)
Giliran 1 Keraguan mengunggah kode karena takut terjadi bentrokan relasi basis data (foreign key). Menanyakan kepastian waktu commit berdasarkan kriteria deadline. Penawaran Solusi Arsitektur: Menyarankan pemisahan tabel authentication agar tidak memicu keraguan bentrok relasi.
Giliran 2 Kebingungan mengenai standar kelayakan draf mentah yang boleh masuk ke repositori. Meminta pengunggahan kode secara utuh. Penyederhanaan Ekspektasi: Memperbolehkan push draf mentah kasar dengan komitmen bantuan penyelarasan rute API dalam tenggat 10 menit.

C. Perbandingan Skema Basis Data (Sebelum vs Sesudah Commit)

Skema Sebelum Commit (Draf Lokal Mendasar - Terhambat Dependency Conflict):

-- Draf Awal (Lokal - Terhambat Konflik Relasi)
CREATE TABLE users (
    user_id INT PRIMARY KEY,
    username VARCHAR(50),
    auth_token TEXT, -- Tergabung langsung, memicu keraguan struktur
    created_at TIMESTAMP
);

Skema Sesudah Commit (Terisolasi & Disetujui Tim):

-- Skema Hasil Commit (Branch Main - Terverifikasi)
CREATE TABLE users (
    user_id INT PRIMARY KEY,
    username VARCHAR(50) NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE auth_sessions (
    session_id INT PRIMARY KEY,
    user_id INT REFERENCES users(user_id) ON DELETE CASCADE,
    auth_token TEXT NOT NULL,
    expires_at TIMESTAMP NOT NULL
);
